# cchub 设计方案（讨论稿）

> 状态：可验证的框架已完成（私有仓库 `Anziron/cchub`），业务功能未开始。项目名 `cchub` 为暂定。
> 最后更新：2026-10-31。讨论来自 Windows 设备（pc-company）上的一次会话。

## 0. 项目目标（2026-10-31 确定）

构建一个注意力优先的 Claude 长任务监督系统。用户离开界面时任务继续运行，只有需要决定时才被通知，并能在 10 秒内看懂上下文、做出决定。

硬约束，先落实再写协议：

1. **进程存活**：`hubd` 崩溃或升级不影响运行中的任务。
2. **状态一致**：在指定弱网条件下，与 `.jsonl` 逐事件一致，需要人介入的事件零丢失。
3. **全部介入类型**：审批、提问、方案确认、中断都有一等界面。
4. **安全边界**：校验 Origin 和设备身份，工具输出不能注入界面。

协议只解析信封，大内容按需获取。兼容性结论由录制回放测试证明，CI 覆盖多个 CLI 版本。

验收指标：

| 验证项 | 指标 |
|---|---|
| 同步可靠性 | 1～2 秒抖动加 5% 丢包下回放真实会话，最终内容与 `.jsonl` 逐事件一致，审批事件零丢失 |
| 显示延迟 | 积压恢复后，1 秒内显示最新状态 |
| 进程安全 | 运行中 `kill -9 hubd`，`claude` 任务不中断，重启后接回 |
| 通知速度 | 从服务器发出审批请求到系统通知，P99 小于 1 秒 |
| CLI 兼容 | CI 回放各版本录制数据，遇到未知事件安全降级，不崩溃 |

## 1. 背景与要解决的问题

现在的用法：设备上执行 `cc`，经 SSH 连到中枢服务器，在 sshfs 挂载的项目目录里运行 Claude Code 的终端界面（TUI）。设备之间经 Tailscale 互通。

体验差的原因：

- 终端界面远程绘制，每次按键都要往返服务器（约 160ms），整屏实时重绘，输入有延迟。
- 后台任务挂在 tmux 里，看不到进度，需要审批时也收不到通知。
- 断网或关窗口后要手动回到 tmux。

目标：做一个轻量的专用客户端，只用来和服务器上的 Claude 对话、看进度、审批。不做编辑器，不装插件。

## 2. 总体架构

服务器跑一个常驻服务 `hubd`，桌面端只负责界面。桌面端不直接运行 `claude`，也不直接 ssh。

```
桌面端 ──WebSocket(Tailscale)──► hubd ──► claude 进程（-p stream-json 无界面模式）
                                  │            │
                                  │            └─ 在挂载目录里读写项目文件
                                  └─ 挂载命令（默认 cc-mount）──sshfs──► 设备上的项目目录
```

| | 服务器端 `hubd` | 桌面端 |
|---|---|---|
| 职责 | 启动和管理 `claude` 进程、挂载项目、转发消息、后台任务 | 显示会话、输入、审批、系统通知 |
| 断网时 | 照常运行 | 显示离线，重连后补齐消息 |
| 运行方式 | systemd 托管 | 托盘常驻 |

部署模式：**一人一套**。每个使用者在自己的服务器上部署自己的 `hubd`，用自己的 Claude 订阅账号。不做多人共用一台 `hubd`（要做用户隔离，且订阅账号多人共用可能违反条款）。

## 2.1 代码结构（2026-10-31）

- `protocol/`：线路消息、信封分类、`sans-IO` 同步核心。`Event` 和 `Skipped` 各覆盖 `out` 文件的一段字节区间 `[seq, next)`，客户端只要连续推进就能证明没有缺口。
- `client/`：桌面端连接逻辑，放在 Rust 进程，窗口关闭后也能维持；不依赖 Tauri，可在 Linux 上测试。
- `server/`：`hubd`，进程托管接口有 systemd 和 direct 两种实现；另有 `fake-claude` 回放录制数据。
- `desktop/`：Tauri 壳，前端只走 IPC，CSP 不允许前端直接连外部。
- `web/src/generated/`：由 Rust 类型生成，CI 检查不漂移。

已验证（2026-10-31）：模拟测试覆盖丢消息、断线、重启；端到端测试含 `kill -9 hubd`，并与配对 `.jsonl` 比对；真实 `claude` + systemd 跑通；变异测试确认测试能发现缺陷。musl 静态二进制约 1.0MB，空闲内存约 952KB（只是框架，业务实现后要复测）。

身份校验：只能监听回环或 Tailscale 地址；监听 Tailscale 地址时必须配置 `HUBD_ALLOWED_USERS`，每次升级连接用 `tailscale whois --json` 核对账号，查不到一律拒绝；带 Origin 的连接一律拒绝。2026-10-31 从设备实连：允许的账号 101，其他账号 403，带 Origin 403。

日志跟读用 inotify，空闲时只有 5 秒一次的状态检查，有项目目录时另有 10 秒一次的设备探测。进程已结束且超过保留期（默认 7 天）的会话目录每天清理；运行中的 `out` 文件不清理，长时间运行时会一直增长。

未做：大内容按需获取、桌面窗口的实际运行和内存实测。

## 3. 已定的决定

| 项目 | 决定 |
|---|---|
| 服务器端 | Rust 单个静态二进制，目标常驻内存约 5～10MB，空闲 CPU 接近 0 |
| 驱动方式 | 直接启动官方 `claude` CLI 的 stream-json 模式，不用 Agent SDK，不需要 Node |
| 存储 | 不用数据库。会话记录直接用 `claude` 自己的 `~/.claude/projects/<路径>/*.jsonl` |
| 账号 | 用服务器上 `claude` 已有的订阅登录，不需要 API Key |
| 桌面端 | Tauri 2 + React + Vite，先做 Windows；手机端以后再说 |
| 进程数 | 不设固定上限，按服务器可用内存自适应（见第 5 节） |
| 审批 | 沿用服务器自己的权限模式（当前是 `auto`），需要人决定的在桌面端弹窗并发系统通知 |
| 界面风格 | 参考 Claude 桌面端：简约、留白多、浅色和深色主题；不使用 Anthropic 的 logo 和品牌素材 |
| 兼容 | 原来的 `cc` 命令照常可用；app 开的会话在终端 `/resume` 也能接上 |
| 代码仓库 | 私有仓库 `Anziron/cchub`，放在 pc-home 的 `D:\frame\buspi\cchub`（独立仓库，`buspi` 经 `.git/info/exclude` 忽略） |
| 目录结构 | `server/` hubd、`desktop/` Tauri、`web/` 前端、`protocol/` 共用类型 |

轻量原则：服务器端只做转发和进程管理，只解析事件信封（类型、序号、状态），不解析正文，不渲染。Markdown、diff、高亮、搜索全部在桌面端做。

### 桌面端资源约束

本地设备还要跑别的程序，桌面端同样以轻量为准。选 Tauri 的原因：用系统自带的 WebView2，不像 Electron 自带 Chromium（Electron 应用通常 200～300MB）；Rust 主进程只有几 MB 到十几 MB。原生界面库（egui、Slint）更省，但难做出想要的观感。

| 场景 | 做法 |
|---|---|
| 关窗口、缩到托盘 | 销毁窗口和 WebView，只留 Rust 主进程维持 WebSocket 和系统通知；再打开时重建（约 0.5 秒） |
| 空闲 | 不轮询，服务器有事件才推；没有常驻动画；窗口不在前台时暂停等待动画 |
| 逐字输出 | 字符先缓冲，每帧最多刷新一次界面 |
| 长对话 | 虚拟列表，只渲染可见消息；历史分页加载，不一次读完 `.jsonl` |
| 代码高亮、diff | 消息进入可视区或展开时才计算；轻量高亮库，按需加载语言 |
| 终端标签页 | xterm.js 打开时才加载，关闭即释放 |
| 依赖 | 不引入大型 UI 框架和图表库，样式用 CSS |

资源目标（开发验收标准，以实测为准）：

| 状态 | 内存 | CPU |
|---|---|---|
| 在托盘，窗口已关闭 | < 20MB | 接近 0 |
| 窗口打开，空闲 | < 150MB（含 WebView2） | 接近 0 |
| 正在逐字输出 | 略有上升 | 单核 < 5% |

## 4. CLI 验证结果（2026-10-30，claude 2.1.314）

在服务器 `/tmp` 下实测，测试文件和会话已清理。

启动命令：

```bash
claude -p --input-format stream-json --output-format stream-json --verbose \
  --permission-prompt-tool stdio [--resume <session-id>] [--include-partial-messages]
```

- 输入输出都是一行一个 JSON。启动后先发 `{"type":"control_request","request_id":"init1","request":{"subtype":"initialize"}}`，返回的 `control_response` 里有可用命令和技能列表（可用于输入框 `/` 补全）。
- 用户消息：`{"type":"user","message":{"role":"user","content":"..."}}`。
- 输出事件：`system`（subtype `init` 带 `session_id`、`tools`、`cwd`；`thinking_tokens`）、`assistant`（content 里有 `text`、`thinking`、`tool_use`）、`user`（工具结果）、`rate_limit_event`、`result`（一轮结束，带 usage 和用时）。
- 审批：权限规则没覆盖的操作，CLI 发出 `{"type":"control_request","request_id":"…","request":{"subtype":"can_use_tool","tool_name":"Bash","input":{…},"description":"…","permission_suggestions":[…]}}`；回复 `{"type":"control_response","response":{"subtype":"success","request_id":"…","response":{"behavior":"allow","updatedInput":{…}}}}` 后才执行。拒绝用 `behavior: "deny"`（细节见下方实测）。`permission_suggestions` 可用于“总是允许”。
- 允许列表里的操作（如 Write）直接执行，不发审批请求。
- `--resume <id>` 冷启动约 1.5 秒完成初始化，会话 ID 不变，上下文保留。
- 单个新进程约 210MB；长会话会涨（实测运行 4.5 小时的会话 396MB）。
- CLI 自带 `--bg`、`claude agents`、`attach`、`logs` 后台会话功能，但只针对终端界面，不能推结构化消息，暂不依赖。
- 内置命令（2026-10-30 验证，用不保存会话的临时进程）：初始化返回的命令列表共 73 个，含 `clear`、`compact`、`config`、`context`、`model`、`usage`，不含 `resume`。
  - `/usage`：返回文字，含当前 5 小时窗口已用百分比、本周已用百分比、各自重置时间，以及最近 24 小时、7 天的请求数和会话数。
  - `/context`：返回 Markdown 表格，含模型、上下文已用 token、各类占用（系统提示、工具、记忆文件、技能）。
  - `/cost`：订阅账号下内容与 `/usage` 相同。
  - 以上都在本地生成，不调用模型、不消耗额度，每次约 2 秒；作为普通回复用 Markdown 显示即可，不需要专门界面。
  - `/model`、`/config` 在列表里，但终端里会弹选择菜单，无界面模式下的表现未验证。
  - 未验证：在已有会话进程里执行这些命令，输出是否会写进会话记录、是否影响上下文。

### 介入类消息实测（2026-10-31，claude 2.1.314）

实验脚本在 `docs/experiments/`；脱敏的回放数据在 `testdata/recordings/`，由 `tools/record/record.py` 生成。人工介入都经 `can_use_tool` 到达；`AskUserQuestion`、`ExitPlanMode` 带 `requires_user_interaction: true`，可用来区分“要人回答”和普通审批。

| 操作 | 格式与结果 |
|---|---|
| 提问 | 请求 `input.questions[]`；回复 `behavior: "allow"`，`updatedInput` 为原 input 加 `answers: {问题文字: 选项 label}`。模型收到答案并继续 |
| 方案确认 | `input.plan`、`input.planFilePath`。**第一次可能是空 `{}`**，要能处理没有方案内容的请求。`allow` 后直接开始执行 |
| 拒绝 | `behavior: "deny"`，`message` 原样成为 `is_error` 的工具结果，模型继续这一轮。拒绝方案后模型会修改并再次发起 |
| 中断 | 请求 `{"type":"control_request","request_id":"…","request":{"subtype":"interrupt"}}`，0.1 秒内返回 `control_response`（含 `still_queued`）、一条 `[Request interrupted by user for tool use]` 和 `result`；前台子进程被结束，进程存活，下一条消息正常 |
| CLI 自身拦截 | `sleep 60; echo` 这类命令不发审批，直接返回带 `<tool_use_error>Blocked:` 的工具结果，界面要原样显示 |

模型可能把前台命令自行改成 `run_in_background: true`，这时一轮会先结束、任务还在跑，界面不能把“一轮结束”等同于“任务完成”。

### 控制消息和内置命令（2026-10-31 实测，脚本 `docs/experiments/cli.py`）

- 切换模型用控制消息 `{"type":"control_request","request_id":"…","request":{"subtype":"set_model","model":"sonnet"}}`，返回 `control_response` 带完整模型 ID，下一轮生效。
- **`/model haiku` 不可靠**：回复“Set model to Haiku”，但之后的请求仍用原模型。界面的模型切换必须走 `set_model`，不能发 `/model`。
- `/config` 不弹菜单，只返回用法文字；要改设置用 `/config key=value`。
- `/model`、`/config`、`/context`、`/usage` 都在 0.5 秒内返回，走普通的 `result`。输出**会写进 `.jsonl`，模型也能看到**，会占上下文，界面不应自动定时调用。
- 中断后的 `result` 是 `subtype: error_during_execution`、`is_error: true`，要按“已中断”显示，不算任务失败。

### 桌面端实现依据（2026-10-31 实测，claude 2.1.314）

- `out` 默认没有用户消息，加 `--replay-user-messages` 才回显（`content` 是字符串，带 `uuid`、`timestamp`）。窗口重建靠从头重放 `out`，所以这个参数是必需的。
- 客户端的回复不进 `out`，请求是否已回答要看后面有没有同 `tool_use_id` 的 `tool_result`；进程退出或一轮结束时未回答的请求作废。
- “总是允许”：`allow` 回复加 `updatedPermissions`（原样用 `permission_suggestions`），CLI 把规则写进 `.claude/settings.local.json`。

### stream 与 `.jsonl` 的对应关系（2026-10-31 实测，单次短会话）

- `assistant`、`user` 事件的 `uuid` 能对上（stream 4 个全部出现在 `.jsonl` 的 5 个里），`message.id`、`tool_use_id` 也一致，可以作为“逐事件一致”的比对键。
- `.jsonl` 里没有 `control_request` 和逐字片段（类型列表中未见），审批请求不能靠 `.jsonl` 恢复，运行中的进程以 `out` 文件为准。
- 两者结构不同，`.jsonl` 还有 `api-request-blob`、`atis-latch` 等内部类型；桌面端显示历史和实时消息需要统一成同一种事件。
- 开 `--include-partial-messages` 后，`stream_event` 占 `out` 的 65%（55KB / 85KB）。
- FIFO 方式配合 `--resume` 可用：2.6 秒答对上文，会话 ID 不变，历史不重放，历史内容必须另外从 `.jsonl` 读。

## 5. 会话与进程管理

- **会话**：磁盘上的对话记录，数量不限，不占内存。
- **进程**：会话执行任务或刚用完时才有一个 `claude` 进程。
- 启动新进程前读 `/proc/meminfo` 的 `MemAvailable`：
  1. 够用（默认至少 300MB，可配置）→ 启动。
  2. 不够 → 结束最久没动的空闲进程，再检查。
  3. 仍不够（其他都在执行任务）→ 排队，界面显示“等待资源”。执行中的任务不打断。
- 空闲回收：默认空闲 10 分钟结束进程，可配置，0 表示不回收。下次发消息用 `--resume` 自动拉起。
- 可选的进程数上限，默认不限。
- 同一会话不能同时被 app 和终端驱动，`hubd` 要检测并提示。
- 进程内存过大（如超过 500MB）时提示 `/compact` 或开新会话。
- **进程托管**（2026-10-31 实测通过）：每个 `claude` 跑在独立的 systemd unit 里，`exec claude … <>in >>out`，`in` 是 FIFO，`out` 是普通文件。
  - 实测：前台工具运行中 `kill -9` 模拟的 `hubd`，unit 仍在运行，工具完成，这一轮正常结束；之后新连接发消息正常；无人连接时产生的审批请求留在 `out` 中，10 秒后回复仍然生效。
  - 对照：普通管道模式下父进程被杀，当前工具能做完，但约 21 秒后 `claude` 随之退出，会话无法继续。
  - `claude` 用 `<>` 自己持有 FIFO 写端，所以不会读到 EOF。启动时有竞态：FIFO 的最后一个 fd 关闭时缓冲数据会丢失，`hubd` 必须先打开 FIFO 并持有到收到第一个事件。
  - `out` 的字节偏移可以直接作为事件序号，`hubd` 重启后从记录的偏移接着读（设计推断，未实现）。进程结束后才清理 `out`。
  - 未验证：真实 `hubd` 重启接回、`--resume` 与此方式组合（实验用了 `--no-session-persistence`）、无 systemd 环境的替代方案。
- `hubd` 和 `claude` 分开 cgroup：`MemoryMax` 对同一 unit 内的子进程同样生效（2026-10-31 实测：32M 限制下子进程申请 100MB 被 OOM 杀掉），`claude` 必须放到独立 unit 或 scope。
- 每个会话只在内存里缓存最近一段事件用于断线补齐，更早的内容由桌面端读 `.jsonl`。

## 5.0 设备离线时的行为

实测（2026-10-31，claude 2.1.314，sshfs 参数与 `cc-mount` 相同）。用单独的测试挂载经本地转发器走 SSH，冻结转发器模拟断网，脚本在 `docs/experiments/`（`offline.py`、`fwd.py`）。

| 场景 | 结果 |
|---|---|
| 断网后读未缓存文件 | 约 57 秒后返回 `Input/output error`，普通工具错误，模型继续这一轮 |
| 断网期间 `claude` 进程 | 存活，未崩溃，没有 D 状态进程残留 |
| 断网时在该目录冷启动新进程 | 40 秒内没有任何输出和报错 |
| 恢复网络 | 约 10 秒内后续工具调用正常；断网时启动的进程也恢复并完成了请求 |

结论和做法：

- `claude` 不会自己暂停，模型把断网当作普通文件错误，可能据此得出错误结论。不能依赖 CLI 的行为来实现“暂停并提示”。
- `hubd` 独立探测每个挂载的健康状态，作为协议里单独的“设备状态”，与连接状态、会话状态分开显示。
- 设备离线时：通知用户；用户消息由客户端暂存，审批回复照常发送；不在该目录冷启动进程。正在运行的这一轮不打断，但醒目提示其中的文件错误可能由离线造成。
- 探测方式（2026-10-31 实测，脚本 `docs/experiments/freeze.sh`）：`hubd --probe` 子进程查一个每次都新的文件名，答复“不存在”算在线，5 秒超时或其他错误算失败，连续 2 次失败判离线，一次成功恢复。断网后 `stat` 已缓存的文件 0 秒成功，所以不能查已有文件。卡住的探测进程收到 `SIGKILL` 后进入 D 状态，恢复网络才退出，因此同一路径同时只跑一个探测；恢复网络后 1 秒内探测成功。
- 写到一半断网（2026-10-31 实测）：`dd` 约 60 秒后返回错误，设备上留下只写了一部分的文件（200MB 中的 2.6MB）。恢复后不会自动清理，界面要提示离线期间的写入可能不完整。
- 模型的反应（2026-10-31 实测一次，haiku，脚本 `docs/experiments/react.py`）：断网后工具卡到 120 秒超时被转到后台，结果里有 Python 报错但 `is_error: false`，170 秒时这一轮仍未结束，设备上留下 4.8MB 的残缺文件。模型不会及时判断出断网，界面的设备状态提示不能省。
- 未验证：真实关机或休眠、`max_conns` 下的并发。

## 5.1 消息同步要求（硬性）

背景：现在经 SSH 用终端界面时，传的是整屏画面（每次刷新几十 KB），SSH 单条 TCP 通道必须按顺序送达。网络一抖（实测 ping 偶尔 2.2 秒），画面积压，本地要把旧画面逐帧补完，显示内容落后服务器很久，两边对不上。tmux 同样会积压。新方案必须避免这种情况：

1. **只传内容，不传画面**：传结构化事件（新增文字、工具调用、工具结果、审批请求、一轮结束、会话状态）。实测工具结果中位数 415B，但 P99 188KB、最大 373KB，大内容只推摘要，展开时再取。
2. **积压时跳过中间状态**：每个连接有发送队列上限。队列积压时，`hubd` 丢弃还没发出的逐字片段（partial），只保留完整消息和最新状态，保证桌面端看到的始终是服务器当前进度。完整消息、审批请求、一轮结束这些事件不能丢。
3. **编号补齐**：每个会话的事件带递增序号。桌面端记录收到的最后序号，重连或发现序号跳跃时向 `hubd` 请求补发；超出 `hubd` 内存缓存范围的部分，从 `.jsonl` 读取。不允许出现“缺了一段但两边都不知道”。
4. **状态分开显示**：界面上分开显示“连接状态”（已连接、重连中、已断开）和“会话状态”（执行中第几步、等待审批、空闲），用户能分清是在等 Claude 还是在等网络。
5. **心跳**：WebSocket 心跳约 15 秒，断线后自动重连并补齐，不需要用户操作。

参考数据（2026-10-30，pc-company 到服务器，Tailscale 直连）：往返约 168ms，执行完成到桌面端收到约 0.1 秒；偶发抖动 1～2 秒。

## 6. 通用化（给别人部署）

- 只硬依赖 `claude` CLI。启动时检查是否安装、是否登录、版本是否支持 stream-json 和审批请求。
- 项目挂载可替换：默认调用 `cc-mount`（按 `hub-setup` 搭建的环境）；也可配置成自定义挂载命令，或直接用服务器本地目录。设备登记文件路径等放配置文件，不写死。
- 连接：默认只监听 Tailscale 地址，用 `tailscale whois` 识别来访设备；不用 Tailscale 时可选访问令牌，不建议直接暴露公网。
- 发布：`hubd` 出 x86_64、arm64 Linux 二进制和安装脚本（装 systemd 服务和默认配置）；桌面端出 Windows 安装包，首次打开填服务器地址。作者自己的环境可通过 `agent-config` 的 `cc-config apply` 安装。
## 7. 界面设计（初稿）

```
┌────────────┬─────────────────────────────────────┐
│ 新建会话     │  litellm_work · pc-company    ⚙     │
│            ├─────────────────────────────────────┤
│ 项目        │   你：帮我修一下登录接口              │
│ ▸ litellm  ●│   Claude：先看一下现有代码。          │
│ ▸ docshub  ○│   ▸ 读取 auth.py                    │
│ 最近会话     │   ▸ 运行 pytest（3 个失败）          │
│  修登录接口  │   ┌ 需要审批：rm -rf build ──────┐  │
│            │   │ [允许] [拒绝] [总是允许]      │  │
│            │   └──────────────────────────────┘  │
│            │   ● 正在执行… 12s                    │
│ 内存 400MB  ├─────────────────────────────────────┤
│            │  输入消息…（/ 弹出命令）  [中断][发送] │
└────────────┴─────────────────────────────────────┘
```

- 左栏：会话按项目分组，圆点表示状态（执行中、等待审批、空闲、已休眠、排队中），底部显示服务器可用内存。
- 打开项目：选本机文件夹（自动换算成 `设备:路径`，等同在该目录执行 `cc`）、最近项目，或手动选其他设备和路径。
- 文字、代码、表格按 Markdown 正常渲染。需要单独处理的消息：

| 消息 | 显示方式 |
|---|---|
| 工具调用 | 一行摘要（“运行 `npm test`”“编辑 `src/app.ts`”），点开看详情；Edit 显示 diff |
| 思考 | 默认折叠成“思考了 N 秒” |
| 审批请求 | 消息流里的卡片：允许、拒绝、总是允许 |
| 待办（TodoWrite） | 固定区域原地更新 |
| 子代理（Task） | 折叠成一块，显示子任务和进度 |
| 逐字输出 | 开 `--include-partial-messages` |

- 等待状态：执行中（见下方“执行状态行”）、等待资源、正在恢复会话（约 1.5 秒）、断线提示条。
- 执行状态行：终端界面里的 “Composing…” 是 TUI 自己画的，stream-json 里没有，由桌面端按事件自己显示。只做简单版：
  - 一行状态，按当前事件显示：思考中（`thinking` 块）、正在回复（`text` 块）、正在运行 `npm test` / 正在编辑 `app.ts`（`tool_use` 的工具名和参数）、等待审批（`can_use_tool`）。
  - 已用时间：桌面端从发出消息开始计时，一轮结束时用 `result` 里的准确用时。
  - 中断按钮（也支持 Esc）。
  - 一个简单的动态点，窗口不在前台时暂停。
  - 不做：随机俏皮状态词、精细动画、实时 token 计数（一轮结束后显示总数即可）。
- 内置命令：`/usage`、`/context` 等直接作为普通回复显示（见第 4 节）。`/resume` 不可用，用历史会话列表代替；模型切换用下拉框，走 `set_model`（`/model` 不生效）。
- 可选（以后再说）：从 `/usage` 文字里提取 5 小时窗口已用百分比，在左栏底部和服务器内存一起显示。
- 第一版不做：文件浏览和编辑、插件、手机端、多用户。
- 备用：终端标签页（xterm.js 直接 ssh 跑原生 `claude`），优先级低。
- 订阅账号拿不到计费数据，只显示每轮 token 数。
